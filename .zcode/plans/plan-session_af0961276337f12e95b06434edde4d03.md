# 折叠调度器重设计:从常数带→学习型跑道控制器

## Context(为什么改)

用户实测感受:压缩频繁、两次压缩间隔太短;触发时机与压缩幅度应由观测驱动而非常数驱动;拒绝补丁式修复,要求整体重设计。

**根因诊断**(基于两份全量盘点):
1. **触发带锚定在预算比值上,不在观测上**。当前:trigger = budget × 0.85 锚点,随 fill/growth 压力**下滑**(越忙越早折),floor 0.65 / ceiling 0.92 全是常数。增长越快的会话越频繁触发——这正是"频繁、间隔短"的机制来源,且没有任何环路让它在被投诉时变宽。
2. **环路只学摘要过冲,不学节奏与幅度**。targetDeviationEma 只修正"落点比目标高多少"(摘要体积估计误差),幅度(memory floor 0.55)与节奏(min-interval = clamp(4×EMA, 5min, 60min))是纯常数。
3. **可用的学习信号全部在采集、零个被消费**:cache 命中率账本有记录无读者(折一次废一次 KV 前缀——折得太频的干净可测信号);`fold_quality:recalled`(摘要是否被回读——幅度是否该更深的干净信号)无人读;growthEma 有但只用于"越忙越早折"的反向滑移。

**设计原则**(延续已确立的纪律):常数=安全边界;测量=学习信号;伪装学习的常数降级为冷启动先验。学习型锚点引入后,growth/fill 的"越忙越早折"下滑**反转**为由故障证据驱动的 k 伺服(400/接管→提前,健康→推迟)。

## 设计:runway(跑道)控制器

每个折叠周期(上次落点→本次触发)产出一份**周期报告**,喂三个 EMA;三个学习量决定下次的触发点与幅度;常数退居边界与冷启动。

### 学习状态(SessionCounter 扩展 + 路由先验 KV)

| 状态 | 含义 | 更新点 |
|---|---|---|
| `runwayEma` | 交付跑道:surfAtFold − landedPrev(token) | 每次折叠提交 |
| `cycleTimeEma` / `cycleRequestsEma` | 周期时长 / 请求数 | 每次折叠提交 |
| `cycleCacheHitEma`(路由级) | 周期缓存命中率 cacheRead/(read+input+write) | 每次折叠提交(registerUsage 累加计数器) |
| `recallEma`(路由级) | 折叠区间被回读比例(fold_quality:recalled + expand_restore 量) | 每次折叠提交 |
| `runwayFactor k`(路由级) | 跑道系数:健康→升(间隔变长),400/接管→降(提前) | 周期报告 + 故障事件 |

持久化:SessionCounter JSON(注意 **restoreCounter 白名单必须同步**——targetDeviationEma 的历史教训);路由先验 KV `fold-cycle:prior:<route>`(仿 deviation-prior 模式)。

### 控制律(planCompaction 替换锚点)

```
anchor   = clamp(landedPrev + k × runwayEma, floor=0.65, ceiling=0.92) × budget   ← 学习点(替换 0.85 锚 + growth/fill 下滑)
amplitude = baseBand × amplitudeFactor(recallEma)                                  ← 学习点(替换固定 band 语义)
             recall 高(摘常常被回读)→ 因子<1 幅度变浅;长期零回读 → 因子>1 幅度变深
target   = anchor − amplitude,clamp [memoryFloor, anchor − minBand]
minInterval = clamp(cycleTimeEma × 0.5, 5min, 60min)                               ← 替换 4×EMA 常数
```
- **故障伺服**:`noteAgentOverflow`(已有)与 guard 接管事件 → k ×= 0.7(提前折);连续 N 周期无故障且 cacheHit 低于路由基线 → k ×= 1.15(上限封顶)。常数 0.7/1.15/N 为冷启动先验。
- **保留不动**:opportunity/intent 接缝微调(带内取整,真正有用)、全部硬边界(floor/ceiling/minBand/memory floor 0.55/0.35、fit-guard、net-saving 闸、deep-probe)、fit-guard 应急门与 stall 逻辑。
- **操作者显式钉住**:`compress_trigger_ratio`/`compress_target_ratio` 显式设置 → 锚点钉死为操作者值,学习让位(仿 `isSummarizationTimeoutExplicit` 先例)。
- **冷启动**:k=1.0、runwayEma=路由先验(无则 baseTriggerRatio−targetRatio 的默认带)→ 首折行为≈现状,随后自适应。

### 周期报告(可观测性)

每次折叠提交发一行 `fold_check / fold_cycle:` 账本:runway、cycleTime、requests、cacheHit、recall、k、amplitude 全参数——下次生产检验直接读数。

## 明确不做

- 不动 base 引擎/overflow 恢复/thinking-guard 的既有职责;不动取代链/遗忘子系统(0.8.16-0.8.20 刚落地)。
- 不引入 LLM 参与调度决策(纯本地算术,零额外请求)。
- 不删旧常数定义(保留为边界),只改"谁决定操作点"。

## 验证

1. `npm run typecheck` + 全量 vitest(现有 517 + 新增伺服/不变量测试)。
2. fuzz:随机 growth/recall/cache 序列下,学到的 trigger/target 永在硬边界内;故障注入后 k 单调下降。
3. 冷启动等价性:无学习状态时首折 plan 与当前 0.8.21 行为数值一致(快照断言)。
4. 发布 v0.9.0(行为反转属 minor 边界跨越),双侧安装后验收:账本 `fold_cycle:` 行的 runway/cycleTime 应逐周自延长;"压缩频繁"的直接度量 = cycleTimeEma 趋势向上。
